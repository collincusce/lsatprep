# LSAT Prep Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build a comprehensive LSAT prep web app (LR + RC + LG toggleable) with 4,000 pre-generated questions, AI-powered grading / explanations / coach / diagnostics via a Lambda proxy to Anthropic's API, deployed to GitHub Pages + AWS free tier.

**Architecture:** Vanilla-JS SPA on GitHub Pages + single Node.js 20 Lambda behind a Function URL + localStorage-only persistence with export/import JSON merge. Question bank is a static artifact generated offline through a 6-stage pipeline (research → taxonomy → coverage → generate → critic → assemble) using parallel Claude Code subagents.

**Tech Stack:**
- Frontend: HTML / vanilla JS ES modules / CSS custom properties / service worker (no framework, no build step)
- Backend: Node.js 20 on AWS Lambda / Function URL streaming / `@anthropic-ai/sdk`
- Generation: Claude Code subagents; artifacts as JSON
- Deploy: `gh` CLI (Pages) + `aws` CLI (Lambda) + bash scripts; scoped IAM user `lsatprep-deployer`
- Testing: `node --test` for pure modules; CI integrity validator for question bank; LG solver double-duty (gen + runtime)

**Design doc:** [`docs/plans/2026-04-19-lsatprep-design.md`](./2026-04-19-lsatprep-design.md)

**Phases:**
1. Project scaffolding (Tasks 1–9)
2. Generation pipeline — infrastructure (Tasks 10–17)
3. Generation pipeline — research & taxonomy (Tasks 18–24)
4. Generation pipeline — produce 4,000 questions (Tasks 25–32)
5. Frontend foundation (Tasks 33–46)
6. Frontend modes — drill, timed, test, writing, coach, progress (Tasks 47–62)
7. Lambda backend (Tasks 63–74)
8. Deployment (Tasks 75–86)
9. Integration, smoke, handoff (Tasks 87–92)

**Total: ~92 tasks.** Each task is 2–20 minutes. Phases 2–4 include longer subagent-run tasks (20–60 min); these are explicitly marked.

### Task 11: Write LG constraint solver — tests first

**Files:**
- Create: `generation/scripts/lg-solver.mjs`
- Create: `generation/scripts/lg-solver.test.mjs`

**Rationale:** This solver runs at both generation time (validate generated games) and frontend runtime (defense in depth). Must be correct. TDD applies perfectly.

**Step 1:** Write failing tests covering:
- A basic linear game with 4 positions, 4 entities, one "X before Y" rule → returns exactly 8 valid permutations (example values to calibrate)
- A game with no solutions returns `[]`
- A game with a conditional rule "if X is in 1 then Y is in 3" is evaluated correctly
- A game with "exactly one of X, Y is in position 2" is evaluated correctly

```javascript
// lg-solver.test.mjs
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { solveGame } from './lg-solver.mjs';

test('basic linear: X before Y', () => {
  const result = solveGame({
    entities: ['A','B','C','D'],
    positions: [1,2,3,4],
    rules: [{ type: 'before', a: 'A', b: 'B' }]
  });
  assert.equal(result.length, 12); // 4!/2
});

test('unsatisfiable rules return empty', () => {
  const result = solveGame({
    entities: ['A','B'],
    positions: [1,2],
    rules: [
      { type: 'at', entity: 'A', position: 1 },
      { type: 'at', entity: 'A', position: 2 }
    ]
  });
  assert.equal(result.length, 0);
});

// ... more
```

**Step 2:** Run tests to verify failure:
```bash
cd lambda && node --test ../generation/scripts/lg-solver.test.mjs
```
Expected: FAIL (`solveGame` not defined).

**Step 3:** Implement `lg-solver.mjs`:
- Export `solveGame({ entities, positions, rules })` returning array of valid assignments.
- Rule types: `at`, `not_at`, `before`, `after`, `adjacent`, `not_adjacent`, `same_group`, `different_group`, `conditional` (if X:Y then A:B), `exactly_one_of`, `exactly_n_in_group`.
- Backtracking search with rule-based pruning.
- Helper `verifyAnswer(game, questionLocalRules, answerText)` that filters solutions by added local rules and checks whether the answer's assertion holds in all/some/none (depending on question type).

**Step 4:** Run tests again — all pass.

### Task 32b: Shard the bank for on-demand loading

**Context:** A single ~10MB `questions.json` forces every visitor to download the whole bank up front. Agreed design (2026-04-20 brainstorm): shard by section × difficulty so the browser loads only the slice a drill / timed section / test actually needs. Static files only — no Lambda involvement; offline mode preserved via service-worker cache.

**Files:**
- Modify: `generation/scripts/assemble.mjs` — emit shards + manifest instead of one file
- Modify: `generation/scripts/validate-bank.mjs` + its tests — validate the sharded layout
- Modify: `frontend/modules/bank.js` + its tests — async lazy-load API
- Modify: `frontend/modules/selector.js` and every caller under `frontend/modules/views/` that uses the bank — await shard loads
- Modify: `frontend/service-worker.js` — cache-first under `bank/` with bankVersion-keyed cache name
- Delete: `frontend/questions.json` (migrate its placeholder content to the shard layout first)

**Shard layout:**
```
frontend/bank/
  manifest.json       # { bankVersion, totalQuestions, shards: [{ path, section, difficulty, idRange: [lo, hi], questionCount, subtypeCounts }] }
  lr-d1.json          # all LR questions at difficulty 1
  lr-d2.json
  lr-d3.json
  rc-d1.json          # RC questions + their passages, grouped per shard
  rc-d2.json
  rc-d3.json
  lg-d1.json          # LG questions + their games + verifiedSolutions
  lg-d2.json
  lg-d3.json
```

Manifest stays tiny: no per-id lookup table — shards are assembled in deterministic id order (`lr-0001..lr-0418` → `lr-d1.json`, etc.) so `getById(id)` uses the manifest's `idRange` to pick the shard.

**New `bank.js` API:**
- `loadManifest()` — async, called in bootstrap. Loads `bank/manifest.json` only.
- `loadShard({ section, difficulty })` — async, memoized. Returns `{ questions, passages, games }`.
- `getById(id)` — async. Resolves the shard from the manifest's id-range table, loads it, returns the question.
- `pickQuestions({ filters, count, seenIds, rng })` — async. Fires only the shard fetches the filter set needs.

**Service worker:**
- Cache-first for `bank/**`, cache name contains `bankVersion`.
- Manifest itself: network-first with cache fallback, so a new `bankVersion` is picked up on first online load.

**Step 1:** Migrate the placeholder bank in `frontend/questions.json` into the shard layout (so dev mode keeps working before the real 4,000-question assembly lands).

**Step 2:** Rewrite `assemble.mjs` to emit shards + manifest. Update `validate-bank.mjs` to validate: every id in every shard falls in that shard's declared `idRange`; no id appears in two shards; manifest totals equal sum of shard `questionCount`s; LG `verifiedSolutions` per game still non-empty.

**Step 3:** Rewrite `bank.js` with the async API. Update `selector.js` and every view that touches the bank (`drill-session.js`, `timed-section.js`, `test.js`, `results.js`, `progress.js`) to await shard loads. Keep a "Loading…" state for first-shard-fetch in each mode.

**Step 4:** Update `service-worker.js` caching policy.

### Task 63: Lambda entry + router

**Files:**
- Create: `lambda/src/index.mjs`

**Step 1:** Implements streamified handler with internal routing:

```javascript
import { streamifyResponse } from 'aws-lambda-streamifying';  // or the runtime provided one
import { writingSample } from './handlers/writing-sample.mjs';
import { explain } from './handlers/explain.mjs';
import { coach } from './handlers/coach.mjs';
import { diagnostic } from './handlers/diagnostic.mjs';
import { verifySharedSecret, respond, corsHeaders } from './lib/http.mjs';

export const handler = awslambda.streamifyResponse(async (event, responseStream) => {
  if (event.requestContext.http.method === 'OPTIONS') {
    return respond(responseStream, 204, '', corsHeaders());
  }
  if (!verifySharedSecret(event)) {
    return respond(responseStream, 401, { error: 'unauthorized' });
  }
  const route = `${event.requestContext.http.method} ${event.rawPath}`;
  try {
    switch (route) {
      case 'POST /writing-sample': return await writingSample(event, responseStream);
      case 'POST /explain':        return await explain(event, responseStream);
      case 'POST /coach':          return await coach(event, responseStream);
      case 'POST /diagnostic':     return await diagnostic(event, responseStream);
      default: return respond(responseStream, 404, { error: 'not found' });
    }
  } catch (err) {
    console.error(err);
    return respond(responseStream, 500, { error: 'internal' });
  }
});
```

# Execution Notes

**Frequent commits:** target one commit per task where it makes sense, or one per small cluster (e.g., all LR rubrics in one commit).

**TDD applies on:** `store.js`, `router.js`, `bank.js`, `selector.js`, `lg-solver.mjs`, `validate-bank.mjs`, `validate-coverage-matrix.mjs`, all Lambda handlers, HTTP helpers.

**TDD does NOT apply on:** generation pipeline stages (qualitative), UI views (manual browser check instead), deploy scripts (smoke test instead).

**Parallelism:** Tasks 25, 26, 27 are the largest wall-clock items (~45–75 min each). They internally dispatch ~25 parallel subagents. Claude Code can run them sequentially or overlap them across phases.

**Dependencies that matter:**
- Task 11 (LG solver) must precede Tasks 12, 27.
- Task 15 (schemas) must precede Tasks 16, 17.
- Tasks 18–24 (research + taxonomy) must precede Tasks 25–27.
- Task 31 (assemble) must precede Task 32, 82.
- Task 75 (IAM user) must precede Task 77.
- Task 76 (Anthropic key) must precede Tasks 77, 79.
- Task 77 (setup-aws) must precede Tasks 78, 79.
- Task 80 (GitHub repo) can happen anywhere after Task 8.

**Abort conditions:**
- If Task 18 research yields no LSAC sample questions (e.g., site changed), pause and reassess few-shot strategy.
- If Task 28/29 critic pass flags >40% of questions, pause — something systemic is wrong with the generator prompts.
- If Task 79 Lambda smoke test fails with 5xx, check CloudWatch Logs and diagnose before proceeding to Task 80.
